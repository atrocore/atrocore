# Upgrade to AtroCore 3.0

This document lists the backward incompatible changes of AtroCore 3.0 and what has to be done about them.

## Subtypes

AtroCore 3.0 adds the entity type **Subtype**. A subtype extends an entity of type **Base** - its supertype - with the fields and relations of one type of its records, e.g. the entity `Foo` with the subtypes `FooTypeSimple` and `FooTypePro`:

- **The data of a record is split between two tables.** The common data stays in the table of the supertype, the data of the type is in the table of the subtype, linked one-to-one by `supertype_id`. A subtype record is deleted by the database together with its supertype record.
- **The supertype gets the `type` field.** It is generated with an option for each subtype - the code of the subtype without the `<Supertype>Type` prefix, e.g. `simple` - and cannot be changed in the Entity Manager. Once an entity has subtypes, each of its records belongs to one of them.
- **A subtype is a full entity in the REST API.** It contains every field and relation of its supertype besides its own ones, and saving it writes both tables.
- **On the UI only the supertype exists.** A record is opened by the URL of the supertype, and the record of a subtype is shown with the layouts of the subtype. Creating a record starts with choosing its type.

Existing entities are not changed by the upgrade.

## Behavior changes

- **A field with `customizable: false` cannot be edited or deleted in the Entity Manager.** The parameter was ignored for single fields before. It now applies to `Listing.product`, `Listing.channel`, `ReportAggregation.period`, `ReportAggregation.periodField` and `AttributePanel.code`, as well as to the generated `type` field of an entity with subtypes.
- **A stream record keeps the definitions of the changed fields.** Each **Update** record stores the type, the label and the options of every changed field in the main language. A change of a field deleted later is shown with the stored definition instead of being hidden. Stream records created before the upgrade do not have the definitions, so their changes of deleted fields stay hidden.
- **An entity with subtypes has one stream.** The changes of the fields of a subtype are recorded in the stream of the supertype record, together with the changes of the common fields. A subtype has no stream, followers and action history of its own.
- **Events of an entity with subtypes.** A change of the common fields is an event of the supertype only. A change of the fields of a subtype is an event of the subtype and of the supertype. The after-save logic of the supertype record - stream, notifications, workflows - runs when both tables are saved.

## REST API

- **`POST /api/<Entity>` is not available for an entity with subtypes.** A record of such an entity is created via its subtype: `POST /api/<Entity>Type<Suffix>`. The `type` field of the supertype is read-only.
- **A subtype record cannot be deleted directly.** `DELETE /api/<Entity>/{id}` deletes the supertype record, which hides its subtype record as well. The subtype record is removed by the database when the supertype record is removed permanently.
- **A record of an entity with subtypes is restored only together with its subtype data.** A record without a subtype record cannot be restored.
- **The `subtype` meta group is added.** `GET /api/<Entity>/{id}` with `With-Meta-Groups: subtype` returns the subtype record in `_meta.subtype` as `{"entityName": ..., "id": ..., "data": ...}`.
- **The relations of the supertype are available via the subtype.** `entityRelation`, link, unlink and the bulk relation endpoints called for a subtype record and a relation of its supertype work with the supertype record.
- **Following a subtype record follows its supertype record.** `POST /api/entitySubscription` and `DELETE /api/entitySubscription` with the name of a subtype subscribe to and unsubscribe from the supertype records.
- **Stream records get two keys in `data`.** `fieldDefs` holds the stored definitions of the changed fields, `subtype` the subtype whose fields were changed.

## Database

- **A subtype table has no `deleted` column.** It holds `id`, `supertype_id` and the columns of the fields of the subtype. A query reading such a table directly has to join the table of the supertype by `supertype_id` and check its `deleted` column.

Any report or integration reading the tables of subtypes directly has to be adapted.

## PHP API

For custom code extending the system:

- **The `deleted` attribute of a subtype is read from its supertype.** In the ORM metadata of a subtype it is an attribute of type `foreign`, as well as every column of the supertype. A raw query must not assume an entity table has the `deleted` column: `Atro\Core\Utils\Database\DBAL\Schema\Converter::hasDeletedColumn()` tells whether it has one, and `Atro\Core\ORM\Repositories\RDB::whereNotDeleted()` restricts a query to the records that are not deleted.
- **An ORM attribute of type `foreign` can have the `proxyType` parameter.** Such an attribute keeps the type of its source column: its value is cast and compared by this type.
- **A belongs-to relation can have the `alwaysJoin` parameter.** The relation is joined to every query of the entity, even when it is not used by the selected fields.
- **`Atro\Core\ORM\Repositories\RDB::completeDeferredSave()` is added.** It finishes a save made with the `skipAfterSave`, `keepNew` and `skipUpdateFetchedValues` options by running the after-save logic.
- **The supertype record carries the fields of its subtype while saved via the subtype.** The fields are added to the entity instance as not storable ones, and `subtypeName` holds the name of the subtype.
- **`Atro\Services\Record::createEntity()` throws `BadRequest` for an entity with subtypes**, and `filterInput()` removes the `type` field of such an entity.
- **`Atro\Services\EntityField::updateEntity()` throws `Forbidden`** for a field with `customizable: false`.
- **`Atro\Core\Utils\Note::getChangedFieldsData()` returns `fieldDefs` and `subtype`** besides the changed fields and their values.
- **The access rights of a subtype are the access rights of its supertype**, and the translations of a subtype fall back to the translations of its supertype.
