# Upgrade to AtroCore 3.0

This document lists the backward incompatible changes of AtroCore 3.0 and what has to be done about them.

## Subtypes

AtroCore 3.0 adds the entity type **Subtype**. A subtype extends an entity of type **Base** - its supertype - with the fields and relations of one type of its records, e.g. the entity `Foo` with the subtypes `FooTypeSimple` and `FooTypePro`:

- **The data of a record is split between two tables.** The common data stays in the table of the supertype, the data of the type is in the table of the subtype, linked one-to-one by `supertype_id`. A subtype record is deleted by the database together with its supertype record.
- **The supertype gets the `type` field.** It is generated with an option for each subtype - the code of the subtype without the `<Supertype>Type` prefix, e.g. `simple` - and cannot be changed in the Entity Manager. Once an entity has subtypes, each of its records belongs to one of them.
- **A subtype is a full entity in the REST API.** It contains every field and relation of its supertype besides its own ones, and saving it writes both tables.
- **On the UI only the supertype exists.** A record is opened by the URL of the supertype, and the record of a subtype is shown with the layouts of the subtype. Creating a record starts with choosing its type.

- **A subtype of a reference data entity has no table.** It is a scope of type **ReferenceData** with `supertypeId`; its records are the records of the supertype with the type of the subtype and have the IDs of the supertype records. The repository, the entity and the service of the supertype serve its subtypes.
- **The value of `type` of a subtype** is the code of the subtype without the `<Supertype>Type` prefix, or `typeOption` of the scope of the subtype, e.g. `Base` for `EntityTypeBase`, `available-currency` for `EntityFieldTypeAvailableCurrency`.

Entities created in the Entity Manager are not changed by the upgrade. The system entities **Connection**, **Storage**, **Action**, **Attribute**, **Entity** and **EntityField** are moved to subtypes, as well as **ExportFeed** of the Export module 2.0 and **ImportFeed** of the Import module 2.0, described in the upgrade notes of these modules.

## Connection

Every connection type is a subtype of `Connection`: `ConnectionTypeSmtp`, `ConnectionTypeMysql`, `ConnectionTypeAtrocore` and so on, as well as the types of the modules, e.g. `ConnectionTypeS3`, `ConnectionTypeMsGraph`, `ConnectionTypeAmazon`. The values of `type` are not changed.

- **The settings of a connection are stored in the table of its type.** The `data` column of `connection` and the `dataField` mechanism are not used anymore: each setting is a column of the subtype table, e.g. `connection_type_smtp.smtp_server`. The upgrade moves the settings of the existing connections to these tables. The `data` column stays in the database and is not read.
- **`Connection` contains only the name, the type and the system fields.** The fields of a type are fields of its subtype, without conditions on `type`. A field that was required for a type is required in its subtype.
- **The secrets that can be long are stored in columns of 2048 characters**, e.g. `apiKeyValue`, `atrocoreToken`, `refreshToken`, `azureSasUrl`. The other password fields keep 255 characters, the encrypted value of a longer secret does not fit there.
- **The REST API creates a connection via its type**, e.g. `POST /api/ConnectionTypeSmtp`; `POST /api/Connection` is not available. `GET /api/Connection/{id}` returns the settings in `_meta.subtype` when the `subtype` meta group is requested. The actions `POST /api/Connection/{id}/test` and `POST /api/Connection/{id}/sendTestEmail` take the ID of the connection record.
- **`useForInstanceComparison` of the Synchronization module is a field of `ConnectionTypeAtrocore`.**

For custom code:

- **The settings are read from the subtype record**: `$connection->getSubtype()->get('smtpServer')`. The ID of the connection record is `supertypeId` of the subtype record.
- **The connection types receive the subtype record.** `connectionFactory->create()` and `Connection::connect()` accept the connection record and pass its subtype record to the connection type, so `ConnectionInterface::connect()` and `$this->connectionEntity` of a connection type work with the subtype record.
- **`Atro\Core\Mail\Sender::send()` takes the connection record** and reads the SMTP settings from its subtype record.
- **A module adds a connection type as a subtype**: the scope `ConnectionType<Type>` with `type: Subtype` and `supertypeId: Connection`, its entityDefs, the detail layout and the service `Atro\Services\ConnectionSubtype` in `app.services`. The class of the type is still registered in `app.connectionTypes`. A module adding fields to `Connection` or extending the conditions of its fields has to move them to its subtype.

## Storage

Every storage type is a subtype of `Storage`: `StorageTypeLocal`, as well as the types of the modules, e.g. `StorageTypeS3`, `StorageTypeCloudinary`, `StorageTypeSharePoint`, `StorageTypeAzureBlob`, `StorageTypeStarkeDms`. The values of `type` are not changed.

- **The settings of a storage are stored in the table of its type**, e.g. `storage_type_local.path`, `storage_type_s3.s3_connection_id`. The upgrade moves the settings of the existing storages to these tables. The old columns stay in the `storage` table and are not read.
- **`Storage` contains only the name, the type, the mounted folder, the activity and the system fields.** The fields of a type are fields of its subtype. The link of a storage to its connection is a field of the subtype, e.g. `StorageTypeS3.s3Connection`.
- **The REST API creates a storage via its type**, e.g. `POST /api/StorageTypeLocal`; `POST /api/Storage` is not available. `POST /api/Storage/{id}/createScanJob` takes the ID of the storage record.
- **The path of a local storage is unique among the existing storages only.** The path of a deleted storage can be used again.

For custom code:

- **The settings are read from the subtype record**: `$storage->getSubtype()->get('path')`, `$file->getStorage()->getSubtype()->get('syncFolders')`. The implementations of the storage types keep receiving the storage record. The subtype record is kept for the request, so reading it repeatedly makes no further queries.
- **The connection of a remote storage** is read by `AbstractRemoteFileStorage::getConnection()` and `AbstractRemoteFileStorage::isAvailable()` from the subtype record of the storage: `$storage->getSubtype()->get($this->getConnectionField())`. The connection type receives the subtype record of the connection.
- **A raw query reading the settings joins the table of the subtype**, e.g. `storage_type_local` by `supertype_id`.
- **The checks of a storage type belong to its subtype**: the local path is validated by `Atro\Repositories\StorageTypeLocal`, the checks of the module types are in the repositories of their subtypes, e.g. `MicrosoftConnector\Repositories\StorageTypeSharePoint`. The detail layouts of the types replace the `StorageLayout` listeners of the modules.
- **A new subtype record gets its `type`** from the default value of the `type` field of the subtype, so the conditions on the type of the supertype fields, e.g. the required mounted folder of a remote storage, work in the create form.

## Action

Every action type is a subtype of `Action`: `ActionTypeUpdate`, `ActionTypeCreate`, `ActionTypeEmail`, `ActionTypeWebhook` and so on, as well as the types of the modules, e.g. `ActionTypeExport`, `ActionTypeImport`, `ActionTypeSuggestValue`, `ActionTypeSendNotification`. The values of `type` are not changed, except for the custom actions.

- **`Action` keeps everything that defines when and how an action is shown and executed**: the name, the type, `executeAs`, `sourceEntity`, `usage`, `display`, `displayField`, `focusField`, `changeFields`, `iconClass`, `massAction`, `inBackground`, the conditions and the relations. The `data` field keeps `fieldData`, `fieldList` and `where`.
- **The settings of a type are fields of its subtype**, e.g. `targetEntity`, `searchEntity`, `updateType`, `updateScript`, `webhookUrl`, `emailTo`, `exportFeed`, `importFeed`, `prompt`. A setting shared by several types is a field of each of their subtypes. The settings stored in `data.field` before are columns of the subtype tables now; the upgrade moves them.
- **A custom action has the type `custom`.** The class of `data/custom-code/CustomActions` is chosen in the `handler` field of `ActionTypeCustom`; the upgrade turns a `custom<Name>` type into the type `custom` with the handler `<Name>`. A new class of `CreateAction` becomes a handler, it needs no change of the database. The labels, names and descriptions of the handlers are in `action.customHandlers` of the metadata.
- **The action set (`ActionTypeSet`) is a subtype of the core that is available when a module enables it**: the Workflows and the PDF Generator modules register `Atro\ActionTypes\Set` as `action.types.set` in the `loadData` method of their metadata listener. Without such a module the action set is not available.
- **The parameters of the transformations of the Renditions module stay virtual fields of `Action`**, they depend on the transformation chosen in `ActionTypeCreateRendition`.
- **The REST API creates an action via its type**, e.g. `POST /api/ActionTypeUpdate`; `POST /api/Action` is not available. The execution routes `POST /api/Action/{id}/<type>` take the ID of the action record.

For custom code:

- **The settings are read from the subtype record**: `$action->getSubtype()->get('targetEntity')` instead of `$action->get('targetEntity')` or `$action->get('data')->field->updateScript`. The action types keep receiving the action record.
- **The class of an action is resolved by `Atro\Core\ActionManager::getActionHandler()`**, which takes the handler of a custom action into account.
- **A raw query reading the settings joins the table of the subtype**, e.g. `action_type_import` by `supertype_id`. The cached rows of the dynamic actions (`dynamic_action`) contain `target_entity`, `show_email_preview` and `email_template_id` of the core types.
- **A module adds an action type as a subtype**: the scope `ActionType<Type>`, its entityDefs, the detail and relationships layouts, the client defs with `views/action/record/detail` and the service `Atro\Services\ActionSubtype` in `app.services`. The class of the type is still registered in `action.types`. A module adding fields to `Action` for its type or extending the conditions of the fields of the core types has to move them to its subtype; its `ActionLayout` listener for the detail layout is replaced by the layout of the subtype.

## Attribute

Every attribute type is a subtype of `Attribute`: `AttributeTypeVarchar`, `AttributeTypeInt`, `AttributeTypeEnum`, `AttributeTypeLink` and so on, as well as `AttributeTypeScript` of the Advanced Data Management module. The values of `type` are not changed.

- **The settings of a type are fields of its subtype**, the same as the parameters of the entity field of this type (`EntityFieldType<Type>`): e.g. `min`, `max`, `measure`, `defaultUnit`, `prefixEnabled` of the numeric types, `maxLength`, `countBytesInsteadOfCharacters`, `notNull`, `isMultilang` of the text types, `options` of the list types, `entityType`, `entityField`, `dropdown` of the link types. The settings stored in `data.field` before are columns of the subtype tables now; the upgrade moves them. `Attribute` keeps the name, the type, the entity, the panel, the group, the requirement and the conditions, the relations and the custom fields.
- **The type of an attribute cannot be changed.** The conversion of an attribute into a script attribute is not available anymore.
- **The REST API creates an attribute via its type**, e.g. `POST /api/AttributeTypeVarchar`; `POST /api/Attribute` is not available. `GET /api/Attribute/{id}` returns the settings in `_meta.subtype` when the `subtype` meta group is requested.
- **The import of an entity with subtypes creates a record via the subtype named by the `type` value of the row** and updates a record via its subtype record, e.g. an import feed of attributes keeps working for the fields of `Attribute`. The settings of a type are imported and exported by a feed of its subtype, e.g. `AttributeTypeEnum` for `options` (see [Behavior changes](#behavior-changes)).
- **The classification attributes are not changed.** Their properties replace the settings of the attribute type as before, and the classification attribute still returns `attributeData` with `field.options`, `field.min` and the other settings.

For custom code:

- **The settings are read from the subtype record**: `$attribute->getSubtype()->get('measureId')` instead of `$attribute->get('measureId')`, `$attribute->getSubtype()->get('options')` instead of `$attribute->get('data')->field->options`.
- **A raw query reading the settings joins the tables of the subtypes.** `AttributeFieldConverter::joinSubtypes()` joins all of them, `prepareSubtypeColumns()` puts the settings of the type of a row under the names of their columns, `getSubtypeColumnExpression()` returns the expression of a setting shared by several types. `Attribute::getAttributesByIds()` and the rows of the attribute field types contain the settings already.
- **The attribute field types read the settings from the columns of the row** (`AbstractFieldType::getSetting()`), not from `data.field`.
- **A new attribute is created via its subtype record**: `$em->getRepository('AttributeTypeFloat')->get()`, set the fields of the attribute and of the type, save. A raw insert writes the row of the subtype table too.
- **The checks of a type belong to the repository of its subtype**, e.g. the deletion of a used option in `AbstractAttributeTypeWithOptions`, the pattern in `AttributeTypeVarchar`. `Attribute::getAttributeData()` returns the data of an attribute with the settings of its type in `field`.

## Entity and EntityField

The Entity Manager works with subtypes. Every entity type is a subtype of `Entity`: `EntityTypeBase`, `EntityTypeHierarchy`, `EntityTypeSubtype`, `EntityTypeReferenceData`, `EntityTypeRelation`, `EntityTypeArchive`. Every field type is a subtype of `EntityField`: `EntityFieldTypeVarchar`, `EntityFieldTypeInt`, `EntityFieldTypeLink`, `EntityFieldTypeLinkMultiple` and so on, as well as the types of the modules, e.g. `EntityFieldTypeAvailableCurrency`, `EntityFieldTypeExportLink`, `EntityFieldTypeComposition`. The values of `type` are not changed.

- **The parameters of a type are fields of its subtype**, with their own detail layout and without conditions on `type`. `Entity` and `EntityField` contain only the common fields, e.g. the name, the code, the type and the tooltip of a field. The parameters of the entities and the fields stay in the same metadata as before.
- **`fields.<type>.params` is removed from the metadata.** The parameters of a field type are the fields of `EntityFieldType<Type>`. The capabilities of a field type are flags of `fields.<type>`: `multilingual` for a type that has language versions, `defaultValue` for a type that has a default value.
- **The REST API creates an entity or a field via its type**, e.g. `POST /api/EntityTypeHierarchy`, `POST /api/EntityFieldTypeVarchar`; `POST /api/Entity` and `POST /api/EntityField` are not available. The types that cannot be created, e.g. `EntityTypeRelation`, `EntityFieldTypeJsonObject`, have `createDisabled` in their scope (see [PHP API](#php-api)). `Entity` and `EntityField` are described in the API documentation.
- **The `supertype` field of `Entity` is renamed to `supertypeEntity`.** It is the supertype of an entity of type **Subtype**; the metadata key `scopes.<Entity>.supertypeId` is not changed. The relations `subtypes`, `supertypeEntity`, `primaryEntity` and `derivativeEntities` point to the subtypes of the respective type, e.g. `EntityTypeBase.subtypes` to `EntityTypeSubtype`.
- **Resetting the configuration to default takes the ID of the record**: `POST /api/Entity/{id}/resetToDefault`, `POST /api/EntityField/{id}/resetToDefault`. `POST /api/Entity/action/resetToDefault` and `POST /api/EntityField/action/resetToDefault` are removed.
- **The preview of a script field takes the ID of the field**: `POST /api/EntityFieldTypeScript/{id}/scriptPreview` with the optional `script` and `outputType` of the form. `POST /api/EntityField/action/renderScriptPreview` is removed, together with the `FieldManagerController` event `renderScriptPreview`. The Advanced Data Management module previews a script attribute via `POST /api/AttributeTypeScript/{id}/scriptPreview`. The response contains `entityName` instead of `entityType`.
- **Changing the code of an option takes the ID of the field**: `POST /api/EntityFieldTypeEnum/{id}/updateOptionCode` and `POST /api/EntityFieldTypeMultiEnum/{id}/updateOptionCode` with `oldValue` and `newValue`. `POST /api/EntityField/action/updateOptionCode` is removed. `Atro\Services\EntityField::updateOptionCode()` and `Atro\Repositories\EntityField::updateOptionCode()` take the ID of the field instead of the entity and the field.
- **The where-filter of a link field is read via the subtype of the field**: `GET /api/EntityFieldTypeLink/{id}/where` and `GET /api/EntityFieldTypeLinkMultiple/{id}/where` with the optional `recordId`. `GET /api/EntityField/{id}/prepareFieldWhere` is removed. A field of another type returns 404 instead of 400.
- **`GET /api/Entity/{id}/fields` is removed.** The fields of an entity are read via `GET /api/entityRelation` with the `fields` relation of `Entity`, or via `GET /api/EntityField` filtered by `entityId`.
- **The available actions of the records come from the server.** A system entity or field cannot be deleted, the ID field cannot be edited, a derived entity cannot be duplicated, and the reset to default is offered for the system entities and fields only. The parameters of an entity not listed in `onlyEditableEmFields` of its scope are returned in `_meta.readOnlyFields` and are not saved.
- **The field types offered when a field is created** are the subtypes of `EntityField`. The server rejects the types that an entity of type **Reference** cannot have.
- **The default value of a field has the type of the field**: `default` of `EntityFieldTypeInt` is an integer, of `EntityFieldTypeBool` a boolean, of `EntityFieldTypeEnum` one of the `options` of the field, and so on, as well as `min` and `max`. The default record of a link field, the default unit of a measure and the default unit of a number are links: the REST API returns and accepts `defaultId`, `defaultIds` or `defaultUnitId`, the metadata of the field keeps them as `default` and `defaultUnit`. A default value set by a script is returned and accepted as `defaultScript`. The default value of a range field is `defaultFrom` and `defaultTo`, a range field has no `default`. The server rejects a default value of a list field that is not one of its options, an empty default value of a required list field and a default unit that is not a unit of the measure of the field; changing the code of an option changes the default value too.
- **The list of entity fields shows the common fields only**: `required`, `readOnly`, `isMultilang` and the other parameters of a type are shown on the record of the field.

For custom code:

- **A module adds a field type as a subtype**: the scope `EntityFieldType<Type>` with `type: ReferenceData` and `supertypeId: EntityField`, its entityDefs with the parameters of the type, the detail layout and the translations. A module adding a parameter to the field types adds it to the entityDefs of the subtypes that have it, e.g. `checkDataQuality` of the Data Quality module.
- **A module adds a parameter of an entity type** to the entityDefs of the respective subtype, e.g. `EntityTypeBase` and `EntityTypeHierarchy`. Its `EntityLayout` listener for the detail layout is replaced by the listeners of the subtypes, e.g. `EntityTypeBaseLayout`.
- **A subtype can refine a field of its supertype** by defining the field without `type` in its entityDefs, e.g. the options of `erasureMode` of `EntityFieldTypeLink`. The definition is merged with the definition of the supertype.
- **`AbstractRecordService::previewScript()` is added.** It renders a script on the first record of the entity of the service, e.g. for the preview of a script field or attribute.
- **`EditableTrait::getReadOnlyFields()` is added.** The fields it returns for a record are returned in the `readOnlyFields` meta group and are not saved; the record views show them read-only.
- **`Atro\Core\Utils\Metadata::getSubtypeScope()` returns the subtype of a supertype for a value of `type`.** The map of the subtypes is in `scopes.<Supertype>.subtypeScopes`.
- **The listeners of the repository events of a supertype apply to its subtypes**, e.g. `EntityFieldEntity::afterSave()` is called when a field is saved via `EntityFieldTypeVarchar`.

## Sorting of records

The order of the records sorted by drag and drop is kept by one mechanism for every entity, with two endpoints instead of the update of a record:

- **The field keeping the order of the linked records is defined by the relation.** `entityDefs.<Entity>.links.<link>.sortField` is a field of the relation entity for a many-to-many relation, e.g. `sortOrder` of `ActionSetLinker` for `Action.actions`, and a field of the foreign entity for a one-to-many relation, e.g. `position` of `SaleItem` for `Sale.saleItems`. The `children` of a hierarchy are sorted by `hierarchySortOrder`, set by the system.
- **The field keeping the order of all records of an entity is `entityDefs.<Entity>.collection.sortField`**, e.g. `sortOrder` of `TranslationRule`.
- **`PATCH /api/entityRelationSortOrder` sorts the linked records** with the body `{"entityName": ..., "id": ..., "link": ..., "ids": [...], "offset": 0}`. `ids` are the linked records in the new order, `offset` is the position of the first of them among all linked records, and the other linked records keep their order around them. The records are numbered 10, 20, 30… and saved one by one, so the hooks of their repositories run. For a subtype record and a relation of its supertype the records of the supertype record are sorted.
- **`PATCH /api/entitySortOrder` sorts all records of an entity** with the body `{"entityName": ..., "ids": [...], "offset": 0}`.
- **The linked records are returned in their order.** `GET /api/entityRelation` without `sortBy` and the repository (`$entity->get('<link>')`, `findRelated()` without `orderBy`) sort the records of a relation with `sortField` by this field. `sortBy` and `asc` of `clientDefs.<Entity>.relationshipPanels.<link>` are the default order only of a relation without `sortField`; they are removed from the panels of the relations with `sortField`.
- **`PATCH /api/<Entity>/{id}` does not sort records anymore.** The keys `_sortedIds`, `_scope`, `_id`, `_link`, `_itemId` and `_previousItemId` are ignored, and the services and listeners handling them are removed, e.g. in `Action`, `Attribute`, `Product`, `ProductFile`, `CategoryFile`, `Component`, `PdfConfiguratorItem`, `ReportAggregation`, `CalculationProfile`, `TranslationRule`, `TransformationParameter` and the items of the sales and inventory documents. `PATCH /api/SynchronizationFeed/sortOrder` is removed.
- **The rows of a relationship panel can be dragged when the relation has `sortField`.** `clientDefs.<Entity>.relationshipPanels.<link>.dragDrop` is removed; a panel disables the dragging with `dragDropDisabled: true`, and its number of records per page is `limit` of the panel or `recordsPerPageSmall` of the configuration. The `listRowsOrderSaveUrl` option of the list view is removed. A list of all records of an entity is draggable with the `dragableListRows` option and `collection.sortField` of the entity.

For custom code:

- **`SortableTrait::updateRelationSortOrder()` and `updateSortOrder()` are added.** A service changes the sorting of an entity by overriding them.
- **`Atro\Core\Templates\Repositories\Hierarchy::updateHierarchySortOrder()`, `Atro\Core\Templates\Repositories\Relation::updateAssociatesSortOrder()` and `Atro\Repositories\Attribute::updateSortOrder()` are removed.**
- **A new link of a product to a category is put at the end of the category.** The sorting of a link of a product to a category is not changed by each save of the link anymore; `Pim\Repositories\Product::updateProductCategorySortOrder()`, `updateSortOrderInCategory()` and `getProductCategoryLinkData()` are removed.

## Behavior changes

- **A field with `customizable: false` cannot be edited or deleted in the Entity Manager.** The parameter was ignored for single fields before. It now applies to `Listing.product`, `Listing.channel`, `ReportAggregation.period`, `ReportAggregation.periodField` and `AttributePanel.code`, as well as to the generated `type` field of an entity with subtypes.
- **A stream record keeps the definitions of the changed fields.** Each **Update** record stores the type, the label and the options of every changed field in the main language. A change of a field deleted later is shown with the stored definition instead of being hidden. Stream records created before the upgrade do not have the definitions, so their changes of deleted fields stay hidden.
- **An entity with subtypes has one stream.** The changes of the fields of a subtype are recorded in the stream of the supertype record, together with the changes of the common fields. A subtype has no stream, followers and action history of its own.
- **Events of an entity with subtypes.** A change of the common fields is an event of the supertype only. A change of the fields of a subtype is an event of the subtype and of the supertype. The after-save logic of the supertype record - stream, notifications, workflows - runs when both tables are saved.
- **The record views of an entity with subtypes use the layouts of the subtype.** The record page, the quick view and the quick edit of a record show the subtype record with the detail, summary, relationships, navigation and insights layouts of its subtype, and the navigation to the previous and next records goes through the list of the supertype. These layouts of the supertype are not used, and the Layout Manager offers them only for subtypes. The selection and kanban layouts are offered only for the supertype. The list layout is offered for both: a subtype uses it in the relationship panels of the entities related to it.
- **An export or import feed of an entity with subtypes works with the fields of the supertype only.** The settings of a type moved to its subtype are not available in a feed of the supertype anymore, e.g. an export feed of `Attribute` does not export `min`, `max`, `options` or `measure`. A feed of a subtype, e.g. `AttributeTypeInt`, works with the fields of the supertype and of the subtype. Feeds configured with the moved fields have to be reconfigured: their configurator items of these fields are not valid after the upgrade.
- **The `supertype` field of a subtype is technical.** It is not available in the layouts, filters, mass update, import, export and the Entity Manager, and is returned by the REST API only.

## REST API

- **`POST /api/<Entity>` is not available for an entity with subtypes.** A record of such an entity is created via its subtype: `POST /api/<Entity>Type<Suffix>`. The `type` field of the supertype is read-only.
- **A subtype record cannot be deleted directly.** `DELETE /api/<Entity>/{id}` deletes the supertype record, which hides its subtype record as well. The subtype record is removed by the database when the supertype record is removed permanently.
- **A record of an entity with subtypes is restored only together with its subtype data.** A record without a subtype record cannot be restored.
- **The `subtype` meta group is added.** `GET /api/<Entity>/{id}` with `With-Meta-Groups: subtype` returns the subtype record in `_meta.subtype` as `{"entityName": ..., "id": ..., "data": ...}`.
- **The relations of the supertype are available via the subtype.** `entityRelation`, link, unlink and the bulk relation endpoints called for a subtype record and a relation of its supertype work with the supertype record.
- **Following a subtype record follows its supertype record.** `POST /api/entitySubscription` and `DELETE /api/entitySubscription` with the name of a subtype subscribe to and unsubscribe from the supertype records.
- **Stream records get two keys in `data`.** `fieldDefs` holds the stored definitions of the changed fields, `subtype` the subtype whose fields were changed.

## Frontend

For custom frontend code:

- **A record of an entity with subtypes is shown by the views of its subtype.** The record page uses `views/subtype/detail`, `views/subtype/edit` and `views/subtype/record/detail` with the model of the subtype record, so the custom detail and edit views of the supertype are not used for such a record. A subtype defines its own detail view in `clientDefs.<Subtype>.views.detail` and its own record view in `clientDefs.<Subtype>.recordViews.detail`; they extend `views/subtype/detail` and `views/subtype/record/detail`. An action of such a view that calls the API of the supertype takes the ID of the supertype record from `supertypeId` of the model. The quick view and the quick edit load the subtype record into the modal of the supertype.
- **The model of a subtype is `models/subtype`.** Deleting it deletes the supertype record, and `getSupertype()` returns the name of the supertype. On the record page the supertype record is available as `model.supertypeModel`.
- **The URLs of a subtype lead to the supertype.** `controllers/subtype` redirects `#<Subtype>/view/{id}` and `#<Subtype>/edit/{id}` to the supertype record and `#<Subtype>` to the list of the supertype.
- **Creating a record of an entity with subtypes starts with `views/modals/select-subtype`.** The create action of the list, the quick create and the modal edit of a new record ask for the subtype first and create the record via the subtype.
- **The custom record views of the Entity Manager are removed**: `views/admin/entity-manager/record/*`, `views/admin/field-manager/detail`, `views/admin/field-manager/record/*`, `views/admin/field-manager/fields/type`, `views/entity/record/panels/fields`. The records of `Entity` and `EntityField` are shown by the standard views of subtypes. A view of a field type reads its parameters from the fields of the subtype instead of `fields.<type>.params`.
- **The views of the default values of the Entity Manager are removed**: `views/admin/field-manager/fields/value-container`, `link-default`, `link-multiple-default`, `measure-default`, `file-default` and `enum-default`. The standard field views take their place with the field parameters `optionsField` of `enum` (the options are the value of another field of the record), `entityNameField` of `link` and `linkMultiple` (the entity is the value of another field of the record) and `foreignFilterFields` of `link` and `linkMultiple` (the records are filtered by the values of the fields of the record, e.g. `{"measureId": "measureId"}`).
- **A record view applies `_meta.readOnlyFields`**, and the duplicate action is hidden when `_meta.availableActions.duplicate` is `false`.

## Database

- **A subtype table has no `deleted` column.** It holds `id`, `supertype_id` and the columns of the fields of the subtype. A query reading such a table directly has to join the table of the supertype by `supertype_id` and check its `deleted` column.

Any report or integration reading the tables of subtypes directly has to be adapted.

## PHP API

For custom code extending the system:

- **The `deleted` attribute of a subtype is read from its supertype.** In the ORM metadata of a subtype it is an attribute of type `foreign`, as well as every column of the supertype. A raw query must not assume an entity table has the `deleted` column: `Atro\Core\Utils\Database\DBAL\Schema\Converter::hasDeletedColumn()` tells whether it has one, and `Atro\Core\ORM\Repositories\RDB::whereNotDeleted()` restricts a query to the records that are not deleted.
- **An ORM attribute of type `foreign` can have the `proxyType` parameter.** Such an attribute keeps the type of its source column: its value is cast and compared by this type.
- **A belongs-to relation can have the `alwaysJoin` parameter.** The relation is joined to every query of the entity, even when it is not used by the selected fields.
- **`Atro\Core\ORM\Repositories\RDB::completeDeferredSave()` is added.** It finishes a save made with the `skipAfterSave`, `keepNew` and `skipUpdateFetchedValues` options by running the after-save logic.
- **`Atro\Core\Templates\Entities\Base::getSubtype()` is added.** It returns the subtype record of a record of an entity with subtypes, e.g. `$foo->getSubtype()->get('amount')`, or `null` when the entity has no subtypes. The record is found by `Atro\Core\Templates\Repositories\Base::getSubtypeRecord()`.
- **The supertype record carries the fields of its subtype while saved via the subtype.** The fields are added to the entity instance as not storable ones, and `subtypeName` holds the name of the subtype.
- **`EditableTrait::createEntity()` throws `BadRequest` for an entity with subtypes**, and `filterInput()` removes the `type` field of such an entity.
- **`Atro\Services\EntityField::updateEntity()` throws `Forbidden`** for a field with `customizable: false`.
- **`Atro\Core\Utils\Note::getChangedFieldsData()` returns `fieldDefs` and `subtype`** besides the changed fields and their values.
- **The listeners of the service of a supertype apply to its subtypes**: a subtype service dispatches the events of the supertype service as well.
- **The layout listeners of a supertype apply to its subtypes**, and the relationship panels of the supertype are shown on the record of a subtype; the subtype can redefine them.
- **The `type` field of a supertype can be defined in its metadata** (view, conditions); the system adds the options of the subtypes to it.
- **`Atro\Core\Templates\Repositories\Base::getSubtypeRecord()` keeps the subtype record for the request.**
- **The access rights of a subtype are the access rights of its supertype**, and the translations of a subtype fall back to the translations of its supertype.
- **`scopes.<Entity>.createDisabled` forbids creating the records of an entity.** Such an entity has no create route, `EditableTrait::createEntity()` throws `NotFound` for it (duplicating included), the `create` action is removed from its `aclActionList`, so the roles have no right to create it, and the ACL of the frontend denies `create` to every user, the administrators included. Every create button, the quick create and the duplicate action of the UI are hidden by this ACL check. It is set for the subtypes of `Entity` and `EntityField` that cannot be created; `clientDefs.<Entity>.createDisabled` keeps hiding the create buttons only.

## Dashlets

The data of every dashlet is returned by one endpoint: `GET /api/Dashlet/{name}`, where `{name}` is the name of the dashlet, e.g. `Channels`. The class providing the data is set as `className` in the metadata of the dashlet, next to its view: `metadata/dashlets/{Name}.json`. A dashlet is not bound to an entity: it can combine the data of several entities. The query parameters of the request are passed to the dashlet, `where` decoded.

- **The dashlet endpoints of the entities are removed.** Their data is returned by the dashlets:

| Removed | Replacement |
|---|---|
| `GET /api/Product/channelStatistics` | `GET /api/Dashlet/Channels` |
| `GET /api/Product/productByStatusStatistics` | `GET /api/Dashlet/ProductsByStatus` or `GET /api/Dashlet/ProductStatusOverview` |
| `GET /api/Product/productByTagStatistics` | `GET /api/Dashlet/ProductsByTag` |
| `GET /api/ImportFeed/syncErrorStatistics` | `GET /api/Dashlet/DataSyncErrorsImport` |
| `GET /api/ExportFeed/syncErrorStatistics` | `GET /api/Dashlet/DataSyncErrorsExport` |
| `GET /api/QualityCheck/statistics` | `GET /api/Dashlet/RecordsByDataQuality` |
| `GET /api/translationStatusStatistics` | `GET /api/Dashlet/RecordsByTranslationStatus` |
| `GET /api/Report/dashletData` | `GET /api/Dashlet/Report` |
| `GET /api/Report/dashletList` | `GET /api/Dashlet/Report?list=true` |

The other parameters and the responses are not changed. The dashlets of the Project Management Customized module (`AliveInstances`, `Efficiency`, `NewInstallations`) keep their URLs.

- **The statistics of the failed import and export jobs of the Synchronization module require the read access to `ImportFeed` and `ExportFeed`.** Before, the access to the not existing scopes `Import` and `Export` was checked.

For custom code:

- **A dashlet with data on the server sets `className` in its metadata**, e.g. `"className": "\\Pim\\Dashlets\\Channels"` in `metadata/dashlets/Channels.json`. The class is placed in `{Module}\Dashlets\{Name}` and implements `Atro\Core\Dashlets\DashletInterface`: `getData(array $params): array` returns the data. Several dashlets can use the same class. A module replaces the data of a dashlet of another module by setting its own `className` in the metadata of this dashlet.
- **The class is obtained from the container**, so its dependencies are injected via the constructor; the per-request `acl` and `user` are read from the container at the time of the call. The class checks the access to the data it reads itself.
- **A dashlet view reads its data from `getDataUrl()`** of `views/dashlets/abstract/base`, which returns `Dashlet/{name}`; the views do not set the URL of their data themselves.
- **The dashlet services are removed.** `GET /api/Dashlet/{name}` does not resolve the `{Name}Dashlet` service anymore. `Atro\Services\DashletInterface` and its alias `Espo\Services\DashletInterface` are removed, as well as `Pim\Services\AbstractDashletService`, `Import\Services\AbstractDashletService`, `Export\Services\AbstractDashletService`, the services `ChannelsDashlet`, `ProductsByStatusDashlet`, `ProductsByTagDashlet`, `DataSyncErrorsImportDashlet`, `DataSyncErrorsExportDashlet` and `Synchronization\Services\DataSyncErrors`.
- **The dashlet methods of the entity services are removed**: `Reports\Services\Report::getDashletData()` and `dashletList()`, `DataQuality\Services\QualityCheck::getQualityCheckStatistics()`, `Translations\Services\Translate::getStatusStatistics()`. The repository methods calculating the data are not changed.

## Services

`{Module}\Services` contains only the services of the entities. Abstract classes and interfaces are in `{Module}\Core`, see the developer guide (Services).

For custom code:

- **`Atro\Services\AbstractService` is moved to `Atro\Core\Services\AbstractService`.** Its alias `Espo\Core\Services\Base` is removed.
- **The headers of the request are read by `Atro\Core\Http\RequestHeaders`**: `RequestHeaders::get($name)`, `isMetaRequested()`, `isMetaGroupRequested($group)`, `getRequestedMetaGroups()` and `getLanguagePrism()`. The static methods `getHeader()`, `getRequestedMetaGroups()` and `getLanguagePrism()` and the methods `isMetaRequested()` and `isMetaGroupRequested()` of the services are removed, e.g. a listener of a service event checks `RequestHeaders::isMetaGroupRequested('availableActions')` instead of `$service->isMetaGroupRequested('availableActions')`. `getHeaderLanguage()` stays a method of the services.
- **The services `App` and `GlobalSearch` are merged into the service `Global`** (`Atro\Services\GlobalService`): `$serviceFactory->create('Global')`. `GlobalSearch::find()` is `GlobalService::globalSearch()`. The static `App::createRebuildNotification()` is removed: a migration calls `$this->rebuild()`, other code `DataManager::pushPublicData('isNeedToRebuildDatabase', true)`.
- **`Atro\Services\Record` and `Espo\Services\RecordService` are removed.** Their methods are distributed between `Atro\Core\Services\AbstractRecordService` (reading the records and their output, extended by every template), the traits of `Atro\Core\Services\Traits` with their interfaces of `Atro\Core\Services\Interfaces` (`Editable`, `Linkable`, `Sortable`, `Deletable`, `SoftDeletable`, `MassActions`) and the templates of `Atro\Core\Templates\Services`. Each template has only the methods of the operations its entity type supports, see the developer guide (Services):
  - **`Archive`** only reads the records.
  - **`ReferenceData`** has no stream, no following, no mass update, delete or restore and no restoring; linking many records at once works via its own linking.
  - **`Relation`** has no stream, no following, no linking and no sorting.
  - **`Subtype`** has no deleting.
  - **`Base`** has the stream and the following, the ownership and the assignment, merging, kanban, the derivatives and the attributes.

  A service extending `Atro\Services\Record` extends the template of its entity type, e.g. `Atro\Core\Templates\Services\Base`; a type hint or an `instanceof` check uses `AbstractRecordService` or the interface of the operation. Code calling an operation for any entity checks that its service implements the interface of the operation; the global endpoints (follow, merge, mass update, delete and restore, link, unlink, sort order, duplicate attributes) return `400` for an entity whose type does not support the operation.
- **The overrides of the templates throwing `BadRequest` or `Forbidden` are removed**: `ReferenceData::massUpdate()`, `massRemove()`, `follow()`, `unfollow()`, `massFollow()`, `massUnfollow()`, `linkEntityMass()` and `Archive::createEntity()`, `updateEntity()`, `deleteEntity()`, `restoreEntity()`, `follow()`, `unfollow()`. The methods do not exist in these templates.
- **`Record::getChunkSize()` is moved to `Atro\Core\Utils\Util::getChunkSize()`.** `getNameField()`, `getLocalizedNameField()` and `getLocalizedNameValue()` are moved to `Atro\Core\Utils\NameField` as `getField()`, `getLocalizedField()` and `getLocalizedValue()`; a service reads it by `getNameFieldUtil()`, other code from the container.
- **The unused members of the record service are removed**: the duplicate check (`checkEntityForDuplicate()`, `getDuplicateWhereClause()`, `processDuplicateCheck()`, `$checkForDuplicatesInUpdate`), `$notFilteringAttributeList`, `$readOnlyLinkList`, `$actionHistoryDisabled`, `$duplicatingLinkList`, `setRelationFields()`, `stripTags()`, `getLocaleId()`, `getFieldByTypeList()`, `hasSuffix()`, `removeSuffix()` and `FOLLOWERS_LIMIT`.
- **The mechanisms are not services anymore.** They are classes of `{Module}\Core`, obtained from the container: `$container->get(\Compliance\Core\Successor::class)`. `ServiceFactory::create()` does not resolve them anymore:

| Removed service | Class |
|---|---|
| `Successor` of the Compliance module | `Compliance\Core\Successor` |
| `Comparator` of the Synchronization module | `Synchronization\Core\Comparator` |
| `TranslateRecord` of the Translations module | `Translations\Core\TranslateRecord` |
| `TwigPdfTemplate`, `OdtPdfTemplate`, `CatalogPdfTemplate` of the PDF Generator module | `PdfGenerator\PdfTemplates\TwigPdfTemplate`, `OdtPdfTemplate`, `CatalogPdfTemplate`; the `handler` of `pdfGenerator.<Entity>.templates.<id>` is the class name, `PdfGenerator\Services\PdfGeneratorInterface` is `PdfGenerator\Core\PdfGeneratorInterface` |
| `ExportType<Type>` of the Export modules | the classes of `{Module}\ExportTypes`, see the upgrade notes of the Export module 2.0 |

- **The service `MassActions` is removed.** `upsert()` is a method of the service `Global`: `$serviceFactory->create('Global')->upsert($data)`. `addRelation()` and `removeRelation()` are methods of the service of the entity (`LinkableInterface`) and do not take the entity name anymore: `$serviceFactory->create('Product')->addRelation($ids, $foreignIds, 'categories', $relationData)`. `upsertViaJob()`, `addRelationViaJob()` and `removeRelationViaJob()` are methods of the service `Global` as well. `addRelationByWhere()` and `removeRelationByWhere()` are removed.
- **The service `DataLineage` is merged into the service `Global`**: `Atro\Services\DataLineage::getTree()` is `GlobalService::getDataLineageTree()`.
- **The abstract classes of the modules are moved to `{Module}\Core`**: `Projects\Core\Services\AbstractService`, and `AbstractEntity` and `AbstractEntityItem` of the Sales module from `Sales\Entities`, `Sales\Repositories` and `Sales\Services` to `Sales\Core\Entities`, `Sales\Core\Repositories` and `Sales\Core\Services`.
- **The unused classes are removed**: `Espo\Services\AdminNotifications` and the entity, repository and service classes `Content` and `ContentGroup` of the PIM module, which have no entity.
- **`Atro\Services\Style` extends `Atro\Core\Templates\Services\ReferenceData`**, the template of its entity type.
- **`Atro\Core\Templates\Services\HasContainer` is removed** with its alias `Espo\Core\Templates\Services\HasContainer`. A service extends `Atro\Core\Services\AbstractService` and adds `container` to its dependencies: `$this->addDependency('container')` in `init()`. `Export\Services\AbstractService` of the Export module is removed.

## Removed deprecated features

The features deprecated in AtroCore 2.x are removed:

- **The field type `jsonArray` is removed.** A list of strings is a field of type `array`, any other JSON value - an object or a list - is a field of type `jsonObject`, which the REST API describes as an object or an array. The fields of the core and the modules are changed accordingly, e.g. `User.disabledLanguages` and `LayoutProfile.favoritesList` are `array`, `conditionalDisableOptions`, `User.dashboardLayout` and `routes` of the hierarchies are `jsonObject`. The values and the SQL types of the columns are not changed; the migration of version 3.0.3 changes the type kept in the comment of the columns to `(DC2Type:jsonObject)`. `jsonArray` stays the storage type of the ORM attributes, e.g. of `array`, `multiEnum` and `linkMultiple`.
- **The field types `arrayInt`, `enumInt`, `enumFloat`, `datetimeOptional`, `duration`, `map` and `colorpicker` are removed** together with their views `views/fields/array-int`, `views/fields/enum-int`, `views/fields/enum-float`, `views/fields/datetime-optional`, `views/fields/duration`, `views/fields/map` and `views/fields/colorpicker`, as well as the library `Colorpicker` of `app.jsLibs`. A color is a field of type `color`. The field type `exportLink` of the Export module is removed with its view `export:views/fields/export-link`. The field type `available-currency` of the PIM module is removed with its view `pim:views/fields/available-currency`. The field types `language` and `multiLanguage` are removed as well: a language of the system is a field of type `enum` with the view `views/fields/language`, e.g. `Component.language`, a list of them is a field of type `multiEnum` with the view `views/fields/multi-language`, e.g. `Channel.locales`. A field of type `arrayInt` is defined as `array`. A number chosen from a list is a field of type `int` or `float` with `options` and the view `views/fields/number-option`, e.g. the options of the dashlets.
- **The Twig functions `convertFileToBase64FromUrl` and `convertAssetToBase64FromUrl` are removed.** A template converts a file with `convertFileToBase64(file, params)`. A template still calling the removed functions fails to render.
- **The transformation script of a data pipeline returns the field values at the top level of the JSON object.** The `targetRecordData` wrapper is not unwrapped anymore: a script returning `{"targetRecordData": {...}}` has to return the content of the wrapper instead.
